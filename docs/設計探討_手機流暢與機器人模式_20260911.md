# 設計探討：手機遊玩流暢度 × 機器人模式（thinking-coach 分析）2026-09-11

> 依據實際程式行為（server.js 624 行／public/index.html 712 行）與設計文件逐行對照的結構化分析。

# 一、現行設計架構盤點

## 狀態機（實際跑法）
```
lobby ──startGame──► admin ──beginRound｜ADMIN_SEC=45s逾時──► choosing
                       ▲                                        │
                       │                       全員submit｜CHOOSE_SEC=45s逾時
              advanceRound(round++)                             ▼
                       │                                    resolveRound
                    reveal ◄── REVEAL_SEC=15s自動 / host於5s後可跳 ──┘
                       │
                    ended ──restart──► lobby
```
- 一切狀態掛在 `rooms` Map；每房 `phase / round / choices{emp,boss,ghost} / config`。
- **計時器全在 server 端**（`startTimer`，server.js:93）：客戶端斷線、切背景、鎖屏都不會卡住遊戲，逾時自動用預設值結算（server.js:186-188）。

## 角色模型
- 四種身分共用 `mkPlayer`（server.js:84）：`role: boss|emp`、`seniority`、動態 `isSupervisor`、`isGhost`。主管與幽靈是「員工的狀態變體」，讓 `submitChoice` 一支處理四種暗選。

## 核心循環：暗選同時結算
- 暗選寫進 `room.choices`，`submitChoice`（server.js:502）末尾為樞紐：湊齊即 `resolveRound`，否則 45s 逾時補預設。
- `resolveRound`（server.js:193-328）固定順序：①幽靈改巡查版圖 → ②道具 → ③老鳥罩學弟 → ④逐員工判被抓/摸魚 → ⑤任務進度與逾期 → ⑥回合末心悸結算與出局 → ⑦冷卻遞減 → ⑧連查限制。

## 撐得住 vs 會卡住

| 面向 | 撐得住 ✅ | 證據 |
|---|---|---|
| 內容擴充 | ZONES/CARD_DEFS/GHOST_ACTIONS/TASKS 皆資料表 | server.js:15-68 |
| 新玩家類型 | 暗選匯流單一入口 `submitChoice`＋單一 `room.choices` | server.js:502-547 |
| 狀態機清晰 | handler 皆 phase 守衛，轉換集中 | 全檔 |
| 結算可決定性 | `resolveRound` 純讀 choices，適合 bot/測試 | server.js:193 |
| 斷線不卡局 | server 端計時器＋逾時預設 | server.js:93,186 |

| 面向 | 會卡住 ⚠️ | 後果 |
|---|---|---|
| **玩家身分 = socket.id** | players Map、choices.emp、hostId 全綁 socket（server.js:383,536,585） | **無重連機制**；bot 無 socket 需到處特判 |
| submitChoice 驗證與寫入耦合 | 驗證+寫入+觸發 resolve 全在 handler（server.js:519-546） | bot 無法重用驗證 |
| resolveRound 就地 mutate | 直接改 e.points/e.anxiety（server.js:256-307） | 無法乾淨 dry-run |
| 無 bot 概念 | mkPlayer 預設帶 socket，無 isBot（server.js:84） | |
| config 依人數推導 | rounds/bossInspect/anxietyOut 由人數決定（server.js:165-168） | bot 補位後「人數」語意需釐清 |

**一句話**：擴充瓶頸不在玩法，在「玩家身分＝一條 socket 連線」——同時卡住手機重連與機器人，是共同前置。

# 二、手機流程摩擦點（嚴重度排序）

### M1｜中途斷線＝永久出局（Critical）
- 證據：`disconnect` 只標 `connected=false` 保留座位（server.js:574-587），但 `joinRoom` 非 lobby 一律拒絕只給觀戰（server.js:392）；localStorage 只存暱稱（index.html:697）。手機鎖屏/切 App socket 斷→回來變新玩家進不了原房；角色每回合被逾時補 idle；若是老闆則 admin 空轉 45s。
- 改法：(A) 持久 playerToken 重連 rebind；**(B) 身分改獨立 playerId(uuid)、socket 只當可替換傳輸指標——順帶解掉 bot 無 socket，一石二鳥，應最先做**。

### M3｜員工單擊即送出、無確認（High）
- 證據：`chooseEmp` 單擊區域立即送出（index.html:375,506），送出後鎖死；老闆/主管都有「確定」按鈕，**誤觸風險最高的員工反而沒有**。道具卡必須在點區域前先選（selCard 隨 payload 送出），順序反直覺。
- 改法：**(A) 員工改兩段式（點選=高亮、底部「確定」送出），選卡併同一步，確定前顯示「將使用 🧃」**——投報率最高的 UX 修正。(C) 允許逾時前改選（server 本可覆寫，前端鎖住了）。

### M2｜admin 階段員工乾等（High）
- 證據：admin 只有老闆有 UI，其他人顯示「老闆行政中…」（index.html:216,434），8 回合 × 最多 45s 發呆。
- 改法：(A) 員工「計畫面板」（手牌/任務/心悸/上回位置，等待變備戰，純前端）；(B) 無事可辦自動略過 admin；(C) 縮短 ADMIN_SEC。

### M4｜資訊密度（Medium）
- 決策必需：心悸（離出局多遠）、任務進度+剩餘回合、lastZone 禁區、老闆巡查數、手牌。
- 可收合：分數、完成率/tasksDone（老闆資訊卻顯示給員工）、log。
- 改法：選擇段「心悸條＋任務＋禁區」放大置頂，其餘折疊。

### M5｜reveal 乾等（Medium）
- 證據：非房主無跳過鈕（server.js:549 只認 hostId）；動畫實長常短於 15s。
- 改法：(A) 全員「我看完了」多數決；(B) REVEAL_SEC 縮 10s；**(C) 每人本地「跳到總結」（純前端，server 計時器仍主導）最省**。

### M6｜語音需 :8443 自簽憑證（Medium，卡入門）
- 手機 getUserMedia 需安全上下文；自簽警告勸退。改法：整站 HTTPS＋正式憑證（Render 版天然解決）。

### M7｜邀請連結明文帶 PIN（Low-Med）
- `?key=PIN` 留在歷史/截圖。休閒場景可暫接受，註記即可。

### M8｜鎖屏背景（Low，已良好）
- `timerEndsAt` 重算自我校正；真正風險是背景過久斷線→併回 M1。

# 三、機器人模式

## 加權比較（滿分 500）

| 準則(權重) | (a)真人老闆·bot員工 | (b)真人員工·bot老闆 | (c)混合補位 |
|---|---|---|---|
| 保留核心樂趣(25) | 3 | 3 | 5 |
| 實作成本(25) | 4 | 2 | 2 |
| AI可信度難度(20) | 4 | 2 | 2 |
| 可重用性(15) | 4 | 3 | 5 |
| 單人完整度(15) | 4 | 2 | 5 |
| **加權總分** | **375** | **240** | **365** |

- **(a) 勝出**：只需一個員工 AI，重用老闆現成 UI；1 真人+2 bot 跑完整迴圈。代價：真人離開「摸魚員工」主角幻想。
- **(c)** 終局形態，但要同時做兩種 AI＋補位＋全套特判。
- **(b) 最差 ROI**：遊戲數學變薄（無同儕爭王、無龜辦公室社交壓力），且老闆 AI「可讀又不被背版」最難。(b) 其實是 (c) 的一種座位配置。

**建議**：MVP=(a)，之後加老闆 AI 升級成 (c)。若試玩發現「當員工才是靈魂」→ 替代 MVP=**(c)-lite**：真人員工＋bot 員工＋腳本化老闆＋**可見的「老闆行為模式卡」**（明示性格傾向，補回讀心樂趣）。用一場試玩決定。

## bot 接入 server.js 的乾淨層次
1. 抽純函式 `buildChoice(room, player, payload) → {choice}|{error}`，socket handler 與 bot 共用（現耦合在 server.js:519-546）。
2. bot 驅動掛狀態進入點：`enterChoose`（server.js:183）為每 bot `setTimeout(computeAndApply, 1–4s 抖動)` 製造思考感（內守衛 phase/房存在）；bot 老闆行政掛 `enterAdmin`（server.js:178）；bot 幽靈同樣在 choosing 排定。
3. 重用湊齊短路：bot 寫完 choices 呼叫共用 `tryResolve(room)`。**resolveRound 完全不動**。
4. `mkPlayer` 加 `isBot:true, socket:null`；disconnect 清房判定改「無真人連線才回收」（server.js:586）→ 正是 M1 playerId 重構順帶解決。

## 員工 bot「像人」要點
- 硬約束天然存在（server 已禁連兩回同區）。
- **softmax 機率抽樣，不要 argmax**——製造人味變異。
- 壓力調節：任務近期限→偏認真/邊摸；心悸近門檻→回辦公室；lastZone 禁區自然換。
- 三風格：貪懶型（廁所/頂樓、耐心悸）／穩健型（平衡早退）／搖擺型（權重平、難預測）→ 真人老闆「學會讀 bot」的樂趣來源。

## 難度
MVP 不做獨立難度旋鈕，用「性格+技巧」純量。日後難度＝調三件事：迴避被巡準度、心悸門檻意識、道具聰明度。

## 單人 vs 多人本質差異與補償
- 流失：讀真人、牌桌笑聲、社交背叛、同儕排名。
- 仍剩：AI 模式預測解謎、任務管理最佳化、心悸 push-your-luck、reveal 動畫爽感。
- 補償：①老闆行為模式卡 ②難度/連勝 meta ③場景卡變化 ④S/A/B/C 評分當單人追分 ⑤具名 bot＋台詞補社交質地。

# 反思與下一步

**三句關鍵 insight**
1. 架構：瓶頸是「玩家身分綁死 socket」——同時鎖住重連與 bot，共同前置。
2. 手機：最痛三件＝斷線無法重連(Critical)、員工單擊即送出(High)、admin/reveal 乾等；前兩者投報率最高。
3. Bot：(a) 是最佳工程 MVP，但用一場試玩確認「當員工」是不是不可放棄的靈魂；接點＝抽純 buildChoice＋掛 enterChoose/enterAdmin，resolveRound 不動。

**建議實作順序**
1. **playerId 重構**（脫鉤 socket.id）——一次解 M1＋bot 前置。最先做。
2. 選擇段兩段式送出＋資訊分層（M3/M4）——純前端，每回合受益。
3. **Bot MVP＝(a)**：buildChoice 抽純＋員工 AI（softmax 三風格）＋enterChoose 驅動。
4. reveal/admin 死時間打磨（M2/M5）＋語音 HTTPS（M6）。
5. 升級 (c)：老闆 AI＋行為模式卡＋難度。
